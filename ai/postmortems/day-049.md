# Day 049 Postmortem — Yabusame Willow Target Archer

## Summary

Day 049 shipped a mobile-first 2D mounted-archery arcade game at the public route `/yabusame/`. The game uses Imagegen2 rider, course, pieces, and icon assets; WebAudio bow/hoof/hit/focus cues; a deterministic debug handle for QA; ordered near/mid/far targets; horse pace/calm/strain pressure; wind drift; focus-arrow and feather-drift mechanics; and a portrait-first 3-column phone control grid.

## What went well

- The archived prompt was created first at `prompts/day-049.md`, then implementation proceeded from that prompt.
- The visual identity is clearly different from recent kiriko, dragonfly, ocean, toy, and dessert games: dusk shrine/riverside course, willow wind, vermilion banners, horse-and-archer silhouette, and target timing rather than puzzle/tabletop mechanics.
- Imagegen2 assets produced a strong gallery thumbnail quickly. The rider asset was alpha-cleaned into a transparent 512px playable sprite and re-inspected before release.
- The route-specific Playwright probe verified menu/tutorial terms, prompt pages, WebAudio initialization, all named controls, visible mechanical effects, pause/resume, restart, Yabusame Focus overlay visibility, forced Grand Hitomi Seal banner, and forced results overlay.
- The mobile 390x844 probe kept HUD, commission card, stage, helper, and all controls inside the first viewport with no page scroll. Touch targets measured above 44px.

## Issues and recovery

- The fresh implementation subagent did not complete a full handoff in the repository. The controller recovered by reading the archived prompt, adopting the partial app shell that existed, generating assets, writing the missing game logic/release artifacts directly, and then launching a separate QA/review pass.
- The first rider asset had a fake checkerboard/white background. The controller alpha-cleaned light neutral pixels, recropped/padded the sprite into a transparent canvas, and re-inspected the optimized result visually.
- The first mobile layout exceeded the 390x844 viewport by about 12px. The mobile CSS was tightened with a fixed 250px portrait stage row, hidden mobile-only master note, smaller gaps, and a compact 3-column control grid while preserving all HUD chips and 44px+ controls.
- The initial prompt HTML checker attempted to rely on `bs4`, which is not installed in the repo environment. It was replaced with a stdlib `html.parser` DOM probe.
- The local Docker readiness loop hit one transient connection reset while Nginx started, then passed the static smoke for `/yabusame/`, `/yabusame/prompt.html`, and `/games/049/prompt.html`.

## Follow-up improvements

- Keep the recovery playbook: if a fresh implementation subagent stalls or produces only partial files, immediately inspect `git status`, choose one owner for each file set, and continue from the archived prompt rather than pushing partial work.
- For character/action sprites, continue requiring transparent cutouts or alpha-cleaning before route smoke; fake checkerboard backgrounds remain common in image generation.
- For 390x844 mobile games with 15 controls, use the 3-column grid and fixed portrait stage row from the first implementation pass rather than trying to fit through a flexible `1fr` stage.
- Keep stdlib prompt-DOM probes available so prompt validation does not depend on optional Python packages.
