# Day 051 Postmortem — Matoi Ember Alley Brigade

## Summary

Day 051 publishes **Matoi Ember Alley Brigade** at `/matoi/`: a mobile-first hybrid/isometric Edo fire-brigade arcade game about moving a brigade leader through smoky alley tiles, rotating braided hoses, pumping water pulses, chaining buckets, raising ladders, rescuing cats, stamping firebreaks, swinging the matoi standard, clearing smoke, and using Ember Focus before wind spreads embers to the shrine gate.

The run followed the prompt-first workflow: the archived prompt was generated before implementation at `prompts/day-051.md`. A fresh implementation subagent was started from only the repo path, day number, archived prompt path, validation/publish rules, and the code-isolation rule. That subagent generated/inspected assets but then stalled without writing Day 051 files to the working tree, so the controller recovered by implementing directly from the archived prompt, while preserving the no-previous-game-source rule.

## Asset QA

Imagegen2 assets were generated for the brigade leader, Edo alley background, pieces sheet, and UI icon sheet, then inspected visually before integration.

- `matoi-brigade.png`: readable Edo fire brigade hero in indigo happi, holding a matoi standard and hose nozzle, facing slightly right. The source used a pale rice-paper background, so the optimized sprite was alpha-cleaned into an RGBA cutout and re-inspected. Final sprite has good crop/pivot margins, no text/watermark/checkerboard, and remains readable at 64–128px.
- `matoi-alley.png`: dramatic portrait Edo alley with blue-black smoke, orange ember glow, wet stone lane, firewatch towers, lantern reflections, and hand pump cart. It is crop-safe for portrait use and leaves an open central lane for the overlaid isometric board, though the lower third is visually rich, so the game renders a darkened board overlay for readability.
- `matoi-pieces.png`: separated ember, water splash, hose bend, bucket, ladder, firebreak plank, smoke tile, wind ribbon, rescue cat, firewatch seal, protected house charm, matoi standard, pressure droplet, and shrine warning on pale paper. No text/watermark/checkerboard; crop margins are generous.
- `matoi-icons.png`: distinct HUD/action icons for movement, hose/pump/bucket/ladder/cat/firebreak/matoi/mist/focus/pressure/morale/smoke/shrine/wind/house/seal/all-clear. No text/watermark/checkerboard; large enough for HUD/button use.

## Control-to-motion and game-feel notes

The implementation exposes visible effects for every named prompt control:

- Move Brigade changes the selected alley tile and moves the hero on the isometric board.
- Rotate Hose changes the visible nozzle/spray preview direction.
- Pump Water sends a visible blue pressure pulse; correct angle weakens/suppresses embers and creates splash rings.
- Bucket Chain creates visible helper markers and restores pressure.
- Raise Ladder draws a ladder and can affect roof fires.
- Rescue Cat collects a visible rescue marker only when near and smoke is safe.
- Stamp Firebreak draws a blue firebreak edge and blocks the next wind tick.
- Swing Matoi expands a visible morale circle.
- Mist Screen renders a smoke-clearing cone and reduces smoke.
- Ember Focus renders a visible gold overlay around fires and rescues and documents predicted spread/pressure/rescue/firebreak cues.
- Pause, restart, prompt, and audio toggle are wired.

WebAudio initializes only after Start and exposes `window.__day051Audio = { ctx, enabled }` for Playwright verification. Audio is non-blocking and the visible game cues remain playable muted.

## QA notes

- Controller route smoke and validation were run after implementation; final command results are recorded in the conversation/report.
- Mobile layout targets a 390x844 portrait viewport with compact HUD chips, incident card, a large board area, helper, and a four-column 44px+ control grid.
- Prompt pages are semantic rendered HTML with a back-to-game link and are not raw Markdown dumps inside `<pre>`.
- Code isolation: the controller did not open, inspect, copy, diff, grep, or adapt previous game implementation source. Previous game source folders and public aliases were not used. Previous metadata, prompts, postmortems, and screenshots were used only for variety analysis before prompt generation.

## Lessons

- The subagent timeout/recovery pitfall remains real: when the fresh implementation pass stalls after asset generation, inspect `git status`, pick one controller owner for Day NNN files, and continue from the archived prompt rather than waiting indefinitely.
- The controller-generated auxiliary assets in `/tmp/day051-imagegen-assets` were useful as a fallback; future runs could pass pre-generated asset paths into a recovery agent if the implementation subagent stalls.
- Pale rice-paper sprite backgrounds can be alpha-cleaned reliably when the hero silhouette is high contrast; re-inspection after optimization is mandatory.
